# План по рекомендациям: cg_players и связанный код (OSP2-PBE)

Источник идей — код devotion. Цель: перенести/адаптировать полезные паттерны для скорости и поддерживаемости.

---

## 1. Вынести HUD-маркер союзника в отдельную функцию

**Статус:** не сделано  
**Приоритет:** высокий  
**Сложность:** низкая  

**Суть:** В devotion маркер союзника вынесен в `CG_FriendHudMarker(cent)` с ранним return по условиям. В OSP2-PBE тот же функционал реализован большим инлайновым блоком в `CG_Player` (~55 строк с трассами, дистанцией, цветом по здоровью, frozen).

**Шаги:**
1. В `cg_players.c` добавить функцию:
   - `static void CG_FriendHudMarker(centity_t *cent, const clientInfo_t *ci, int clientNum, qboolean useTeamFrozen)` (или с теми параметрами, которые уже есть в `CG_Player`: ci, clientNum, useTeamFrozen).
2. Перенести в неё весь блок от проверки `cg_drawHudMarkers.integer && CG_BE_FEATURE_ENABLED(CG_BE_HUD_MARKERS)` до конца блока (включая трассы, wallhack, `CG_HudBorderMarker`).
3. В начале функции сделать ранние return: не team game, зритель, не союзник, сам игрок и т.д. — по образцу devotion `CG_FriendHudMarker`.
4. В `CG_Player` заменить инлайновый блок одним вызовом: `CG_FriendHudMarker(cent, ci, clientNum, useTeamFrozen);`.
5. Проверить: поведение (трассы, видимость, frozen, цвет по здоровью) должно совпадать с текущим.

**Результат:** CG_Player короче и понятнее; при невыполнении условий — один вызов с быстрым return, без лишней работы в горячем пути.

## 2. Отложенная загрузка игроков (deferred loading)

**Статус:** не сделано  
**Приоритет:** средний  
**Сложность:** средняя  

**Суть:** В devotion при входе игрока можно не грузить модель сразу, а пометить `ci->deferred = qtrue` и скопировать модель с уже загруженного клиента; позже в безопасные моменты (scoreboard, счётчик кадров) вызывается `CG_LoadDeferredPlayers()` и по одному подгружаются отложенные. При нехватке памяти (`trap_MemoryRemaining()`) новых не грузят. В OSP2-PBE есть команда `loaddeferred` и комментарии, но самой логики в cgame нет.

**Шаги:**
1. **clientinfo:** добавить в структуру `clientInfo_t` поле `qboolean deferred` (если ещё нет). В `cg_local.h` проверить/добавить.
2. **cg_t:** добавить счётчик для растягивания загрузки по кадрам, например `int deferredPlayerLoading` (как в devotion), обнулять при смене карты/снапа при необходимости.
3. **CG_NewClientInfo / путь создания clientinfo:**  
   - При необходимости отложить загрузку (низкая память или политика «не грузить сразу»): искать уже загруженного клиента с той же моделью/скином/командой; если найден — копировать модель в нового и выставить `ci->deferred = qtrue`. Иначе вызывать обычную полную загрузку.  
   - Реализовать аналог `CG_SetDeferredClientInfo` и вызывать его там, где сейчас сразу грузится модель.
4. **CG_LoadDeferredPlayers:**  
   - Сканировать `cgs.clientinfo[0..maxclients-1]`; для записей с `infoValid && deferred` при `trap_MemoryRemaining() >= порог` вызывать полную загрузку и сбрасывать `deferred`.  
   - Подключить команду `loaddeferred` к этой функции, если ещё не подключена.
5. **Точки вызова:** вызывать `CG_LoadDeferredPlayers()` в безопасных местах — например при отрисовке scoreboard (каждый N-й кадр, как в devotion: `if (++cg.deferredPlayerLoading > 10) CG_LoadDeferredPlayers();`) и при загрузке карты (если нужно).
6. **Отрисовка:** везде, где по `ci` рисуется игрок/ник/иконка, при `ci->deferred` показывать заглушку (крестик/иконка «загрузка»), как в devotion в scoreboard и draw.

**Результат:** меньше фризов при входе нескольких игроков подряд и при нехватке памяти; загрузка моделей размазана по кадрам.

## 3. Таблицы цветов modelRGBA / corpseRGBA

**Статус:** не сделано  
**Приоритет:** низкий (после 1 и 2)  
**Сложность:** высокая  

**Суть:** В devotion цвета по части тела (голова/торс/ноги) и типу (свой/враг/команда/труп) предпросчитаны в `cgs.modelRGBA` и `cgs.corpseRGBA`. В рендере игрока вызывается `CG_PlayerGetColors` → по сути `memcpy` из нужной ячейки (4 байта). В OSP2-PBE цвета задаются через `ci->colors` и OSP (team/enemy/my colors), конвертация float→byte делается в `CG_Player` при заполнении shaderRGBA.

**Шаги:**
1. Ввести в `cgs` (или в OSP-структуру) таблицы вида:
   - `byte modelRGBA[MCIDX_NUM][MODELCOLOR_NUM][4]` и `byte corpseRGBA[...][...][4]` (индексы: часть тела, тип цвета — default/red/blue/team/enemy и т.д.). Константы MCIDX_*, MODELCOLOR_* задать по смыслу OSP.
2. При смене конфига/команд (cvars команд, враг, свой цвет и т.д.) заполнять эти таблицы из текущих строк/float-цветов (один раз при парсинге).
3. В логике выбора цвета игрока: по команде/враг/труп и части тела вычислять индекс в таблице.
4. В `CG_Player` вместо текущего расчёта из `ci->colors` (float→byte по компонентам) использовать выбранный индекс и `memcpy(outColor, cgs.modelRGBA[bodyPart][coloridx], 4)` (и аналог для трупа).
5. Увязать с существующей системой OSP (teamColors, enemyColors, myColors) и с `paintItBlack` — либо оставить paintItBlack поверх таблиц, либо включить «чёрный» вариант в таблицу.

**Результат:** в горячем пути меньше ветвлений и операций; один memcpy(4) вместо нескольких умножений и присвоений. Требует аккуратной интеграции с текущей системой цветов OSP.

## 4. CG_FileExists для поиска моделей

**Статус:** сделано (реализована регистрация клиентов по образцу devotion)  
**Приоритет:** низкий  
**Сложность:** низкая  

**Суть:** В devotion при подборе путей к моделям/скинам используется `CG_FileExists(filename)` — обёртка над `trap_FS_FOpenFile(filename, NULL, FS_READ)` (len>0 → qtrue). В OSP2-PBE добавлены CG_FileExists, CG_FindClientModelFile, CG_FindClientHeadFile; CG_RegisterClientSkin и CG_RegisterClientModelname переписаны по образцу devotion.

**Шаги:**
1. Если в OSP2-PBE появится перебор нескольких путей к моделям (разные папки, префиксы), добавить в `cg_players.c`:
   - `static qboolean CG_FileExists(const char *filename);`
   - реализация: `trap_FS_FOpenFile(filename, NULL, FS_READ)`; return (len > 0).
2. Использовать её во всех местах проверки существования файла вместо дублирования вызова trap_FS_FOpenFile.

**Результат:** один общий способ проверки существования файла; меньше дублирования кода.

## 5. CG_PlayerShadow (порядок проверок)

**Статус:** опционально  
**Приоритет:** низкий  
**Сложность:** низкая  

**Суть:** В devotion тень максимально простая: ранние выходы (cg_shadows==0, invis), один BoxTrace, для типа 1 — ImpactMark. В OSP2-PBE уже есть расширения (BE alt shadow, цвет, cg_shadows -1). Упрощать до точного копирования devotion не нужно; достаточно убедиться, что самые дешёвые проверки идут первыми.

**Шаги:**
1. В `CG_PlayerShadow` проверить порядок: сначала `cg_shadows.integer == 0` и invis — они уже в начале; при необходимости добавить другие ранние выходы до тяжёлых операций.
2. Никаких крупных изменений логики не требуется.
