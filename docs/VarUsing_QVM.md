# QVM: использование cvar и глобалов

Краткие правила по чтению cvars и глобальных переменных в Q3VM (cgame/game/ui). См. также [qvm-architecture.md](qvm-architecture.md) и [qvm-optimization-rules.md](qvm-optimization-rules.md).

---

## Стоимость доступа

- **Одно чтение** `cvar.integer` или `cgs.someField` — одна загрузка 4 байт (LOAD4), ~2–3 цикла. Разницы по операциям нет.
- Чтение cvar **не вызывает** syscall: значение уже в памяти VM (движок синхронизирует vmCvar_t при обновлении cvars).
- Чтение поля структуры (глобал или cvar) — это «адрес + смещение + LOAD4». Дёшево.

---

## Не копировать cvar в cgs «для скорости»

- Копирование в начале кадра: `cgs.shud = cg_shud.integer` и дальше везде `cgs.shud` **не даёт выигрыша** по операциям.
- Каждое чтение — одна загрузка. Было N чтений из cvar → станет 1 запись + N чтений из cgs. Операций не меньше, код сложнее.
- **Правило:** проверять cvar напрямую: `cg_shud.integer`, `cg_drawAmmoWarning.integer` и т.д. Без промежуточного слоя в `cgs`.

---

## Когда кешировать в локальную переменную

- **Кеш в локаль имеет смысл**, только если **получение значения дорогое**: результат `trap_*`, вызов функции, сложный доступ (pointer chase). Тогда: один раз вычислил → записал в локаль → в цикле/дальше только читаешь локаль.
- **Простой int из глобала или cvar:** читай глобал/cvar прямо в условии. Кеш в локаль добавляет одну запись и те же N загрузок (уже из стека) — операций больше, выигрыша нет.
- В цикле «не тащить за собой глобальную область» для одного поля (например, `cvar.integer`) не даёт выигрыша: мы и так читаем только 4 байта по фиксированному смещению, не всю структуру vmCvar_t.

---

## Правила в коде

| Ситуация | Что делать |
|----------|------------|
| Один int/флаг из cvar или cgs | Читать напрямую: `cg_shud.integer`, `cgs.something` (если поле уже есть в cgs по другой причине). |
| Дорогое вычисление (trap, функция) | Один раз вычислить, сохранить в локаль, в цикле/дальше использовать локаль. |
| Несколько проверок одного cvar в одной функции | По желанию можно взять в локаль в начале — по операциям примерно то же, чуть понятнее «одно место входа». Не обязательно для скорости. |

## Использование указателей на структуры (clientinfo, entity и т.п.)

### Что важно понять

- **Указатель кеширует адрес, а не значение.**
- В Q3VM адрес элемента массива (base + index * size) — это несколько инструкций (LOAD + mul + add).
- Если к одному и тому же элементу массива обращаются несколько раз подряд, имеет смысл вычислить адрес один раз и дальше работать через указатель.

### Когда указатель оправдан

2 и более обращения к одному слоту массива в одном логическом блоке, например:

```c
cgs.clientinfo[num].team = ...
cgs.clientinfo[num].health = ...
```

Код находится:

- в цикле,
- или в часто вызываемой логике (игроки, HUD, entity update),
- или просто становится заметно чище.

**Рекомендуемый вариант:**

```c
clientInfo_t *ci = &cgs.clientinfo[num];

ci->team = ...
ci->health = ...
```

**Плюсы:**

- адрес считается один раз;
- меньше повторяющейся адресации;
- код читабельнее;
- легко расширять (добавить третье поле без дублирования).

### Когда указатель не нужен

Одно обращение к элементу массива:

```c
team = cgs.clientinfo[num].team;
```

Нет цикла, нет повторов — выигрыш нулевой, код только усложняется.

### Где объявлять указатель

Максимально узкий scope:

```c
if ( num >= 0 && num < MAX_CLIENTS ) {
    clientInfo_t *ci = &cgs.clientinfo[num];
    ...
}
```

- Указатель объявляется только при валидном индексе.
- Не выносить указатель на уровень всей функции, если он используется в одном блоке.

### Чего НЕ делать

- **Кешировать через указатель одно поле «на всякий случай»:**

  ```c
  int team = ci->team;  /* без причины */
  ```

- **Делать указатель ради одного доступа:**

  ```c
  clientInfo_t *ci = &cgs.clientinfo[num];
  team = ci->team;  /* бессмысленно */
  ```

- **Использовать указатель как замену логики:** если значение может меняться семантически — считывай там, где нужно.

### Связь с правилами про локали и cvar

- **Кеш значения** и **кеш адреса** — разные вещи.
- Кешировать **значение** имеет смысл только если оно дорого получается.
- Кешировать **адрес** имеет смысл, если к нему идут несколько обращений.
- Указатель — это оптимизация адресации, а не доступа к данным.

### Краткое правило

- **Один слот массива, несколько обращений** → используй указатель.
- **Одно обращение** → пиши напрямую.

---

## Итог (расширенный)

- **Cvars и простые глобалы** — читаем напрямую.
- **Значения** кешируем только если получение дорогое.
- **Адрес элемента массива** кешируем указателем, если к нему есть несколько обращений.
- Минимальный scope, валидный индекс, без избыточных локалей.
