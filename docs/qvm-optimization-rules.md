# QVM: основные правила ускорения кода

Краткая инструкция по оптимизации кода для Q3VM (cgame/game/ui). Основано на [qvm-architecture.md](qvm-architecture.md) и [qvm-performance-guide.md](qvm-performance-guide.md).

---

## Контекст QVM

- **Stack-based VM**: LCC не делает inlining, loop unrolling, constant folding.
- **Function call** ≈ 40–50 циклов (ENTER + LEAVE + CALL + ARG).
- **Memory access** ≈ 2–3 цикла (дёшево).
- **Syscalls** — стоимость зависит от движка; минимизировать количество.

---

## Золотые правила

### 1. Inline > функции

- Тривиальный код (1–3 строки) в hot path — **inline вручную**.
- Избегать цепочек: `GetX() → CheckX() → UseX()`.
- Функции оставлять для сложной логики и мест вне hot path.

### 2. Линейный код > ветвления

- Каждый `if` — дополнительные циклы и риск branch misprediction.
- **Early return** вместо глубокой вложенности.
- Объединять проверки: `if (a && b)` вместо `if (a) { if (b) }`.
- Не углубляться: вложенность > 3 уровней — плохо.

### 3. Один проход > несколько

- Один простой цикл часто быстрее «умного» кеша с проверками и обновлением.
- Кеш оправдан только для **дорогих** операций, редко меняющихся данных.
- Избегать фазовой обработки (phase 0 / phase 1) в горячем коде.

### 4. Меньше syscalls

- Culling и проверки — в VM, syscall только когда действительно нужно.
- Кешировать результаты тяжёлых вызовов (например, `trap_CM_BoxTrace`).
- Batch-операции предпочтительнее множества одиночных вызовов (если API позволяет).

### 5. Простота > хитрость

- Меньше опкодов → обычно быстрее.
- «Умные» оптимизации в QVM часто проигрывают простому линейному коду.
- Читаемый код проще поддерживать и дальше оптимизировать.

## Антипаттерны (избегать)

| Антипаттерн | Проблема |
|-------------|----------|
| Getter/Setter цепочки | Много вызовов вместо прямого доступа к полям. |
| Кеш «всё подряд» | Доп. ветвления, состояние, память; часто медленнее простого прохода. |
| Фазовая обработка в hot path | Состояние, задержки, лишние проверки. |
| Глубокая вложенность `if` | Много прыжков, плохая предсказуемость ветвлений. |
| Syscall в каждой итерации цикла | Рост числа переходов VM ↔ движок. |

---

## Что делать в коде

- **Hot path**: проверки и простую логику писать inline, без лишних функций.
- **Циклы**: без вызовов функций внутри; ранний `continue` для пропуска.
- **Условия**: early return, объединённые условия, плоская структура.
- **Syscalls**: вызывать только после отсева (culling); кешировать дорогие вызовы.
- **Алгоритмы**: предпочитать O(n) одному проходу вместо O(n²) со сдвигами (например, packing вместо удаления по одному элементу).

---

## Чеклист по hot path

- [ ] Нет тривиальных getters/setters в горячем коде.
- [ ] Критичная логика inline.
- [ ] Нет вызовов функций внутри горячих циклов.
- [ ] Early return, объединённые условия, без глубокой вложенности.
- [ ] Минимум syscalls в циклах; culling до вызова.
- [ ] Кеш только для дорогих операций; без лишней «умной» логики.

---

## Когда оптимизировать

- **Да**: функции, вызываемые сотни/тысячи раз за кадр; узкие места по профилю.
- **Нет**: код, вызываемый редко; меню/UI; уже быстрые участки (< 0.1 ms).

**Правило:** сначала профилирование, потом оптимизация, затем замер прироста.
